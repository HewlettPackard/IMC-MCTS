How to read this

Stages run in order on the current single-core design. Stage bars include the work shown in their parts and shared memory, so do not add rows together. Cycles start at zero for each computer search. The latest 12 iterations stay available here.

Service bars use the simulator's ordered schedule. Striped control time stays in its owning stage; its exact position and split among controllers are unresolved. FSM shows the four-cycle finish on the current architecture (one cycle on the historical full-expansion engine), with its other control work included in the stages. Parts without separate timing are marked “Included in parent”. Bars show scheduled work, not every cycle a circuit remains electrically active. Human thinking, host game rules and display pauses are outside these cycles.

What is included?

Area shows installed hardware and stays fixed during a run. Energy and average power use the same component estimates as Results and evidence. Uncharacterized parts are excluded from the known totals. Shared blocks count once; Expansion and Backprop share one controller, so their hardware costs stay together.

Latency uses the time spent in each search stage. Memory time is already inside those stages. FSM finish takes four cycles per iteration on the current architecture; other control time stays in its stage. Human thinking, display pauses and host Go processing are excluded. Average power is energy divided by the same simulated time, so the energy and power percentages match.

What is FSM finish?

Four clock cycles finish an MCTS iteration on the current architecture after Backprop. Historical full-expansion runs use one cycle. It belongs to the global finite state machine (FSM). The FSM also controls the other stages; their control time is already included in each stage's cycles. This segment counts only the finishing step.
